# Add a Migration

## Arguments

- `$0` -- Migration description (e.g., `init balance`, `add ledger table`)

## Implementation Steps

### 1. Verify entity exports

Ensure all entities are imported in `backend/domain/entities/__init__.py`. Alembic's `env.py`
imports this module to discover models.

```bash
cat backend/domain/entities/__init__.py
```

### 2a. Autogenerate (PostgreSQL reachable from `.env`)

```bash
just start        # database + redis
just migrate      # bring the local DB to head first
just migration "$0"
```

### 2b. Hand-write (no local PostgreSQL)

Create `backend/infra/database/psql/alembic/migrations/versions/<YYYY_MM_DD_HHMM>_<rev>_<slug>.py`
using the header from `script.py.mako` (`revision`, `down_revision` = current head, `branch_labels`,
`depends_on`). In `upgrade()` mirror the entity exactly: same types (`sa.Numeric(18, 6)`,
`sa.BigInteger()`, `sa.DateTime(timezone=True)`), nullability, `server_default=sa.text("0")` /
`sa.text("now()")`, and constraint names through `op.f("pk_<table>")` / `op.f("ix_<table>_<col>")`
so they match the metadata naming convention. Write a real `downgrade()`.

### 3. Review

Check for: correct column types and constraints, indexes on filtered columns, nullable settings,
server defaults, reversible downgrade. Run the **migration-reviewer** agent for anything beyond a
single new table.

### 4. Verify

```bash
just check
uv run pytest tests/integration/test_migrations.py   # compare_metadata(...) must be []
```

The session fixture of the integration suite runs `alembic upgrade head` on a fresh container, so
`just test` also proves the migration applies.

## Common Issues

- **Empty autogenerated migration**: the entity is not imported in `entities/__init__.py`
- **Drift test fails on a type**: `Numeric` precision/scale or `BigInteger` vs `Integer` differ
  between entity and migration; fix the migration (or the entity if the migration is applied)
- **Renamed columns**: Alembic cannot detect renames -- use `op.alter_column(..., new_column_name=...)`

# Генерации и баланс пользователей

## Запуск

Нужны `uv`, `just`, Docker. Python 3.12 ставится `uv` автоматически.

```bash
uv sync --group=dev
cp .env.example .env
just start          # postgres:18 и redis:8 из docker-compose.local.yaml
just migrate        # alembic upgrade head
just flusher        # фоновый процесс write-behind, Ctrl+C делает финальный flush
```

Проверки и тесты:

```bash
just check          # ruff format, ruff check, mypy --strict, layer guard
just test-unit      # 21 unit-тест, Docker не нужен
just test           # 67 интеграционных тестов, testcontainers поднимают postgres:16 и redis:7
```

Интеграционный прогон занимает около 15 секунд на ноутбуке, плюс старт контейнеров.
Если testcontainers падает на Ryuk (`Port mapping ... 8080 is not available`), задайте
`TESTCONTAINERS_RYUK_DISABLED=true`.

## Обзор

Сервис принимает генерации и пополнения баланса, держит балансы в Redis и периодически
сбрасывает их в PostgreSQL. HTTP API нет, сервисы вызываются из тестов и из фонового процесса
`backend flusher`.

Стек: Python 3.12, asyncio, SQLAlchemy 2.0 (psycopg), Alembic, redis-py (Lua-скрипты),
Dishka, msgspec, pytest + testcontainers.

Модуль `backend/domain/generation.py` (политика списания, контракты и `FakeGenerationProvider`)
взят как есть и не редактируется. Он исключён из `ruff` и из строгой проверки `mypy`, потому что
в исходном виде не проходит ни то, ни другое.

## Схема PostgreSQL

Одна таблица `balance`, одна миграция `backend/infra/database/psql/alembic/migrations/versions/`.

| Колонка | Тип | Назначение |
|---|---|---|
| `user_id` | `UUID PK` | естественный ключ |
| `free_usd`, `bonus_usd`, `paid_usd` | `NUMERIC(18, 6)` | деньги, никогда не `float` |
| `free_requests` | `INTEGER` | бесплатные запросы |
| `version` | `BIGINT` | номер последней версии баланса из Redis |
| `updated_at` | `TIMESTAMPTZ` | время последнего flush |

Таблица пишется только через `INSERT ... ON CONFLICT (user_id) DO UPDATE ... WHERE
excluded.version > balance.version`. Тест `tests/integration/test_migrations.py` сверяет
миграцию с моделью через `alembic.autogenerate.compare_metadata`.

## Архитектура

Четыре слоя: `domain` (`generation.py`, сущность `Balance`, протокол репозитория),
`app` (сервисы и порты), `infra` (PostgreSQL и Redis), `entry` (DI-контейнер и запуск flusher).
`app` не импортирует `infra`, это проверяет `just check`.

Redis, ключи:

| Ключ | Тип | Содержимое |
|---|---|---|
| `bal:{user_id}` | HASH | четыре поля баланса целыми микродолларами (×10⁶) и `version` |
| `bal:dirty` | SET | пользователи с несброшенными изменениями |
| `bal:load:{user_id}` | STRING | лок холодной загрузки из PostgreSQL, `SET NX PX 5000`, значение — токен владельца |
| `gen:{client_request_id}` | HASH | запись генерации: статус, план списания, `reservation_token`, результат, TTL 24 часа |
| `gen:inflight` | ZSET | незавершённые резервы, score = `started_at`. Индекс для reaper |
| `topup:{operation_id}` | STRING | маркер применённого пополнения, TTL 24 часа |

Восемь Lua-скриптов в `backend/infra/database/redis/scripts.py`: `RESERVE`, `SETTLE`, `REFUND`,
`TOP_UP`, `SEED_IF_ABSENT`, `ADVANCE_VERSION`, `RELEASE_LOAD_LOCK`, `CLEAR_DIRTY`. Баланс хранится
целыми микродолларами, поэтому скрипты складывают через `HINCRBY`, без плавающей точки. Только
`RESERVE` сравнивает `version`: его план посчитала политика на снимке. `SETTLE`, `REFUND` и `TOP_UP`
аддитивны, снимок им не нужен, конфликтовать они не могут; `version` они лишь инкрементируют,
чтобы параллельный `RESERVE` перечитал баланс, а flusher увидел изменение. В Python деньги остаются
`Decimal`, `money_to_micros` отказывается от суммы точнее шести знаков.

### `execute_generation`

1. Проверка `model_name` по `MODELS`, иначе `InvalidInputError`.
2. Снимок баланса из Redis. Если ключа нет, холодная загрузка: лок `bal:load`, один `SELECT`
   из PostgreSQL, `SEED_IF_ABSENT`. Остальные процессы ждут 10 мс и повторяют чтение.
3. `DebitPolicyService.authorize(request, snapshot)` в Python. Ошибки доступа пробрасываются
   как есть.
4. `RESERVE`: атомарно проверяет `version`, списывает план, создаёт запись `gen:*` со статусом
   `running`, помечает пользователя грязным. При конфликте версии скрипт возвращает текущий
   баланс, сервис заново вызывает `authorize` и повторяет. Лимит 100 попыток.
5. Вызов провайдера вне любых блокировок, под `asyncio.timeout(PROVIDER_TIMEOUT_SECONDS)`
   (240 секунд, заведомо меньше `REAP_AFTER_SECONDS`): медленного провайдера бросает и возвращает
   резерв сам вызывающий, а не reaper из-под вызова, который вот-вот завершится. Параллельные
   генерации одного пользователя действительно идут параллельно, в тестах `max_active_calls`
   доходит до 30.
6. Успех: `SETTLE` записывает результат в `gen:*` и убирает id из `gen:inflight`. Если провайдер
   выставил счёт меньше авторизованного, разница прибавляется к балансу тем же скриптом через
   `HINCRBY`, без чтения снимка и без повторов. Авторизация является потолком: счёт выше неё
   срезается до авторизованной суммы, в ответе `billed_cost_usd` равен фактически списанному.
   Излишек возвращается в обратном порядке списания (LIFO по политике), `free_requests` не
   возвращаются. Счёт провайдера квантуется вниз до шести знаков (`quantize_money`), остаток
   уходит в возврат: в Redis не может оказаться сумма, которую `NUMERIC(18, 6)` округлил бы при
   flush. Ошибка или таймаут провайдера: `REFUND` прибавляет план обратно и ставит статус
   `failed`, сервис поднимает `GenerationFailedError`.
7. `SETTLE` и `REFUND` проверяют, что запись всё ещё `running`. `SETTLE` различает два способа
   выйти из `running`: `DONE` (запись уже завершена — это повтор того же вызова, ответ на который
   потерялся) возвращает списанную сумму, `STALE` (reaper уже вернул резерв) отбрасывает результат
   и поднимает `GenerationFailedError`. Деньги не списываются дважды и не возвращаются дважды.

Повторная доставка того же `client_request_id`: `RESERVE` видит запись и возвращает её.
`done` даёт закэшированный результат, `failed` повторно поднимает ошибку, `running` ждёт
завершения опросом каждые 20 мс, не дольше 30 секунд. Провайдер вызывается не более одного
раза на `client_request_id` в пределах TTL записи. Другой `model_name` или `dialog_id` с тем же
идентификатором отклоняется как `InvalidInputError`.

### `apply_top_up`

Валидация (суммы не отрицательные, не больше 6 знаков после запятой), затем один вызов `TOP_UP`:
скрипт проверяет маркер `topup:{operation_id}`, прибавляет суммы через `HINCRBY` и ставит маркер.
Снимок не читается, конфликта с параллельными генерациями нет. Если ключа баланса ещё нет в Redis,
сервис делает холодную загрузку и повторяет. Повторная доставка пополнения ничего не делает.

### Фоновый процесс

`backend flusher` раз в `FLUSH_INTERVAL_SECONDS` (1 секунда) читает `bal:dirty`, забирает
балансы пачкой через pipeline и пишет их одним `INSERT ... ON CONFLICT`. Флаг снимается
скриптом `CLEAR_DIRTY` только если версия в Redis не изменилась с момента чтения. Поэтому
изменение во время flush не теряется, а падение процесса между записью и снятием флага даёт
повторный, идемпотентный flush. Несколько экземпляров flusher не мешают друг другу: строки
сортируются по `user_id`, upsert защищён условием по `version`, `RETURNING user_id` сообщает,
какие строки PostgreSQL принял.

Отклонённая строка означает, что PostgreSQL держит версию не ниже прочитанной. Обычно это другой
flusher, успевший записать более новый снимок: Redis уже ушёл вперёд, делать ничего не нужно.
Но если Redis перезапустился с AOF, отставшего от последнего flush, его `version` меньше
версии в PostgreSQL, и каждый следующий flush отклонялся бы, пока версия случайно не перегонит
строку, при этом флаг `bal:dirty` снимался бы как после успешной записи. Flusher отличает эти
случаи: для отклонённой строки он читает строку из PostgreSQL, и если её состояние отличается,
скриптом `ADVANCE_VERSION` (compare-and-set по прочитанной версии) переводит `version` в Redis
на единицу выше версии в PostgreSQL и пишет предупреждение в лог. В гонке двух flusher'ов CAS не
проходит, потому что Redis уже сменил версию. Следующий flush перезаписывает строку: Redis
остаётся источником истины.

В том же тике работает reaper. Он берёт из `gen:inflight` записи старше `REAP_AFTER_SECONDS`
(300 секунд), для каждой со статусом `running` возвращает план в баланс через `REFUND` и ставит
`failed`. Так резерв процесса, упавшего между `RESERVE` и `SETTLE`, возвращается пользователю
без ручного вмешательства. Reaper не трогает PostgreSQL.

Команды `RESERVE`, `SETTLE`, `REFUND`, `TOP_UP` и удаление из `gen:inflight` повторяются до 3 раз
при обрыве соединения с Redis или таймауте (`RETRY_ATTEMPTS`). Повтор безопасен: каждый скрипт
узнаёт собственный уже выполненный вызов, ответ на который потерялся, и не применяет его второй
раз — `RESERVE` по `reservation_token` в записи, `TOP_UP` по маркеру `topup:{operation_id}`,
`SETTLE` по статусу `done`, `REFUND` по проверке `status == running`.

Лок холодной загрузки снимается только владельцем: `bal:load:{user_id}` хранит случайный токен, а
`RELEASE_LOAD_LOCK` удаляет ключ лишь при совпадении. Владелец, переживший TTL, не снимет лок,
который уже взял другой процесс.

## Принятые решения и ограничения

Redis является источником истины во время работы, PostgreSQL получает снимки состояния.
Альтернатива с журналом операций (outbox) дала бы то же окно потери данных и вдвое больше кода.

Списание построено на строгом compare-and-set по `version`. История изменений баланса
получается последовательной по построению: каждый применённый план был посчитан политикой
ровно на том состоянии, к которому он применён. Отсюда инварианты: баланс никогда не уходит в
минус, нельзя потратить больше доступного, каждая выполненная генерация подтверждена политикой.
Возвраты и пополнения только прибавляют, поэтому им снимок не нужен: они выполняются одним
вызовом без цикла повторов, а под нагрузкой конфликтуют только резервы между собой.

Ошибка провайдера кэшируется. Повторная доставка неудавшейся генерации не вызывает провайдера
повторно. Новая попытка требует новый `client_request_id`.

Ограничения:

- Окно потери данных: изменения после последнего flush пропадут, если Redis потеряет данные
  раньше следующего flush. Compose запускает Redis с `appendonly yes` и
  `maxmemory-policy noeviction`, при таких настройках окно равно интервалу flush плюс fsync.
- Окно идемпотентности равно TTL записи (24 часа). Более поздняя повторная доставка считается
  новой операцией.
- Деньги хранятся с точностью шесть знаков после запятой. Счёт провайдера с большей точностью
  округляется вниз, разница остаётся у пользователя.
- Если процесс упал между `RESERVE` и `SETTLE`, резерв возвращается reaper'ом не раньше чем
  через `REAP_AFTER_SECONDS`. Живой вызов провайдера обрывается раньше, через
  `PROVIDER_TIMEOUT_SECONDS`, и возвращает резерв сам; генерация, которая честно длится дольше,
  будет отменена. Оба порога настраиваются, первый должен оставаться больше второго.
- Повторы при обрыве Redis ограничены 3 попытками. Если Redis недоступен дольше, резерв
  останется `running` до reaper'а.
- Распределённый запуск на нескольких машинах не рассматривался.

## Как проверялась корректность

Все интеграционные тесты идут против настоящих PostgreSQL и Redis в testcontainers и
настоящего `FakeGenerationProvider` из `backend/domain/generation.py`. Моков нет. Каждый тест берёт нового
пользователя и чистит Redis.

| Файл | Что проверяется |
|---|---|
| `test_single.py` | все ветки политики: 3 модели, `conditional_free_eligible`, все три ошибки доступа, неизвестная модель, отказ не трогает провайдера и баланс |
| `test_parallel.py` | 30 одновременных запросов одного пользователя: при `paid_usd = 1.00` ровно 5 `premium` проходят, 25 получают `InsufficientBalanceError`, баланс ровно 0, каждый успешный id вызван один раз |
| `test_redelivery.py` | повторная доставка во время выполнения, после успеха, после ошибки, с другим payload, таймаут ожидания |
| `test_provider_errors.py` | возврат резерва при ошибке провайдера, смесь ошибок и успехов с точной суммой, ошибка не блокирует другие диалоги, провайдер медленнее `PROVIDER_TIMEOUT_SECONDS` бросается и возвращается |
| `test_top_up.py` | пополнение всех полей, идемпотентность по `operation_id` (последовательно и 5 параллельных), отрицательные и слишком точные суммы, пополнение параллельно с 30 генерациями, пополнение при пустом Redis |
| `test_cold_cache.py` | баланс есть в PostgreSQL, в Redis нет: один `SELECT` на 30 одновременных запросов, пользователь без строки в PostgreSQL |
| `test_convergence.py` | после `flush_once()` строка в PostgreSQL совпадает с Redis по всем полям и `version`, `bal:dirty` пуст, фоновый `run()` сходится и делает финальный flush при остановке, повторный flush ничего не пишет |
| `test_multiprocess.py` | 3 процесса (`spawn`) по 10 запросов одного пользователя стартуют по барьеру: 5 успехов, 25 отказов, один `SELECT` на всех, PostgreSQL сходится с Redis. Два процесса с одним `client_request_id` дают один вызов провайдера |
| `test_settle_reconciliation.py` | счёт ниже авторизации возвращает излишек LIFO, счёт выше срезается, повторная доставка отдаёт фактически списанное, 11 параллельных генераций с частичным счётом сходятся по инварианту, `SETTLE` переживает обрыв соединения с Redis, счёт точнее шести знаков квантуется и flush совпадает |
| `test_reaper.py` | зависший резерв возвращается, свежий не трогается, завершённые записи выходят из `gen:inflight`, пустой индекс ничего не стоит, фоновый `run()` тоже реапит |
| `test_flusher_conflicts.py` | два flusher'а одновременно на одном пользователе: принята одна строка; медленный flusher не затирает более новый снимок; Redis, перезапущенный с версией ниже PostgreSQL, переводится вперёд и следующий flush перезаписывает строку |
| `test_transport_retries.py` | обрыв соединения после того, как скрипт уже выполнился: `RESERVE` списывает один раз, `SETTLE` не выдаёт ложную ошибку и не возвращает излишек дважды, `TOP_UP` зачисляет один раз |
| `test_migrations.py` | миграция совпадает с моделью |
| `test_load_from_env.py` | все четыре конфиг-класса читаются из окружения; пропущенное обязательное поле и неконвертируемое значение называют поле |
| `test_ioc.py` | контейнер flusher'а собирается без провайдера генераций, с провайдером резолвится `GenerationService` |

Инварианты в параллельных тестах: все поля баланса `>= 0`, `начальный − конечный == Σ billed_cost_usd`,
`provider.get_stats().calls[id] == 1` для каждого выполненного id, `max_active_calls >= 2`.

## Как проверялось снижение обращений к PostgreSQL

Счётчик вешается на событие SQLAlchemy `before_cursor_execute` движка, он видит каждый SQL
запрос приложения и ничего лишнего (`BEGIN`, `COMMIT` и инициализация драйвера через него не
идут). В многопроцессном тесте каждый процесс возвращает свой счётчик.

Измерено в `test_pg_budget.py`, `test_cold_cache.py` и `test_multiprocess.py`:

| Сценарий | SQL-запросов |
|---|---|
| 30 генераций, баланс в PostgreSQL, Redis пуст, затем `flush_once()` | 1 `SELECT` до flush, 1 `INSERT ... ON CONFLICT` после, итого 2 |
| ещё 30 генераций при тёплом Redis, затем `flush_once()` | 1 |
| `flush_once()` без изменений | 0 |
| 3 процесса по 10 генераций, Redis пуст | 1 `SELECT` на все процессы, 1 upsert при flush |
| 30 генераций и пополнение параллельно, тёплый Redis | 1 при flush |

Число обращений к PostgreSQL не зависит от числа генераций. Оно равно одной загрузке на
пользователя за время жизни ключа в Redis плюс один upsert на пачку грязных пользователей за
интервал flush.

## Что бы сделал при наличии времени

- Журнал операций в PostgreSQL (`generation`, `top_up`) тем же write-behind для аудита.
- Метрики: конфликты CAS, холодные загрузки, размер пачек flush.
